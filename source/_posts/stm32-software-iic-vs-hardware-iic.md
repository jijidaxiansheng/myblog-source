IIC 这个问题在 STM32 面试里非常常见。表面上大家都知道一句“硬件 IIC 靠外设，软件 IIC 靠 GPIO 模拟”，但如果继续追问“为什么硬件 IIC 更省 CPU”“软件 IIC 为什么更灵活”“项目里到底该怎么选”，很多回答就开始发散了。

所以我把这部分单独整理成一篇。目标不是背定义，而是把两种方案背后的执行逻辑、优缺点和适用场景讲透。

<!-- more -->

## 一、先用一句话说清两者的根本区别

软件 IIC 和硬件 IIC 的根本区别，不在于协议本身变了，而在于：

**I2C 总线时序到底是谁生成的。**

- 硬件 IIC：由 MCU 内部的 I2C 外设模块自动生成时序。
- 软件 IIC：由 CPU 控制普通 GPIO，再配合延时函数“手搓”时序。

也就是说，不管是哪一种，最终都要在 `SCL` 和 `SDA` 上形成符合 I2C 协议的波形。区别只是在于，这个波形是“硬件自动输出”还是“软件一点点翻出来”。

## 二、硬件 IIC 到底在替我们做什么

很多人会把硬件 IIC 理解成“库函数更方便”，但这其实说浅了。

硬件 IIC 真正的价值在于：**把 Start、Stop、地址发送、ACK 检测、时钟驱动、数据移位这些底层细节交给专用外设状态机处理。**

CPU 在这个过程中做的事通常是：

- 配置时钟和工作模式
- 写入从机地址
- 写入或读取数据寄存器
- 等待标志位、中断或者 DMA 完成

所以硬件 IIC 的核心优势不是“少写几行代码”，而是：

- 时序由硬件生成，边沿更稳定
- 可以和中断、DMA 配合
- CPU 不需要自己盯着每一个时钟跳变

## 三、软件 IIC 的本质，其实是 Bit-Banging

软件 IIC 常被叫成“模拟 IIC”，更准确一点其实就是 `Bit-Banging`。

也就是 CPU 自己按协议要求去做这些事：

- 让 `SDA` 拉高或拉低
- 让 `SCL` 拉高或拉低
- 控制好每一段延时
- 在正确时刻采样应答位和数据位

如果把它想象成一个画波形的过程，就比较直观了：

- 硬件 IIC：你把指令交给外设，它自己画
- 软件 IIC：你自己拿笔一笔一画去描

所以软件 IIC 的好处和问题都很明显：

- 好处是灵活，任意 GPIO 都能用
- 问题是全程占 CPU，而且时序质量很依赖代码执行环境

## 四、两者最关键的差别，放在 5 个维度里最容易比较

### 1. 工作原理

- 硬件 IIC：专用外设状态机生成总线时序
- 软件 IIC：CPU 直接翻转 GPIO 并插入延时

### 2. CPU 占用

这是两者非常本质的差异。

硬件 IIC 里，CPU 往往只负责“发命令”和“取结果”。如果配合中断或者 DMA，CPU 在传输期间还能去做别的事。

软件 IIC 则基本相反。发送一个字节时，CPU 得负责：

- 拉数据线
- 拉时钟线
- 延时
- 再拉下一位

所以软件 IIC 在传输期间通常是阻塞式的，CPU 占用明显更高。

### 3. 通信速率和时序精度

硬件 IIC 更容易做到：

- 标准模式 `100 kHz`
- 快速模式 `400 kHz`
- 更高模式下的稳定时序

因为它的节拍来自专用外设和时钟分频逻辑。

软件 IIC 的速率则取决于：

- CPU 主频
- GPIO 翻转速度
- 延时函数精度
- 中断是否打断当前节奏

所以软件 IIC 通常更适合低速、可控、对实时性要求不高的场景。

### 4. 引脚灵活性

这一点恰好反过来。

硬件 IIC 通常要走芯片指定的 I2C 复用引脚，灵活性受芯片封装和引脚复用能力限制。

软件 IIC 只要有两个空闲 GPIO，就能自己定义 `SCL` 和 `SDA`。这在下面这些场景里非常有用：

- 板子已经布完线，硬件 I2C 引脚被占了
- 芯片资源紧张，没有多余硬件 I2C 控制器
- 临时调试某个器件，不想大改硬件

### 5. 可移植性和调试体验

硬件 IIC 的底层代码一般会更依赖具体芯片：

- 换了厂商，寄存器和库函数不一样
- 换了系列，初始化方式和事件标志也可能变

软件 IIC 则更像一套纯逻辑代码：

- 拉高
- 拉低
- 读引脚
- 延时

只要把 GPIO 操作宏和延时函数换掉，整体框架很容易搬到别的平台上。

## 五、为什么很多人觉得 STM32 的硬件 IIC“有时候不如软件 IIC 省心”

这也是一个很现实的问题。

理论上硬件 IIC 明显更高级，但在实际开发里，很多人反而会在某些项目里主动换成软件 IIC，原因通常有两个：

### 1. 部分系列或历史库的使用门槛偏高

尤其是早期 STM32 标准库里，I2C 的事件和状态机步骤比较绕。一旦 `START`、地址应答、重复起始、最后一个字节的应答控制没处理好，就容易卡在等待事件上。

所以很多人会有一种体感：不是协议难，而是硬件外设的状态机和库封装不够直观。

### 2. 软件 IIC 更容易“看见过程”

软件 IIC 的每一步都是自己写出来的：

- 什么时候拉低 `SDA`
- 什么时候拉高 `SCL`
- 什么时候读应答

出问题时，你可以非常直接地打断点、看逻辑分析仪、对照代码定位哪一步节奏不对。这种可控感在调试阶段其实很有价值。

## 六、项目里到底怎么选，别只背“硬件快、软件灵活”

如果只是背一句“硬件快、软件灵活”，其实还不够落地。我更喜欢按场景来判断。

### 适合优先选硬件 IIC 的场景

- 设备需要长期稳定运行
- 通信频率较高
- 总线上挂了多个器件
- 希望配合中断或 DMA 降低 CPU 占用
- 板级设计已经把 I2C 专用引脚留好了

这类场景里，硬件 IIC 往往更符合“工程长期维护”的方向。

### 适合考虑软件 IIC 的场景

- 只挂 1 到 2 个低速器件
- 引脚复用受限，硬件 I2C 引脚不方便用
- 项目更看重快速落地和好调试
- 需要跨平台复用一套简单驱动
- 某些特定芯片的硬件 I2C 外设在历史上口碑一般

这类场景里，软件 IIC 反而经常是更省心的解法。

## 七、一个面试里比较稳的回答方式

如果面试官问“软件 IIC 和硬件 IIC 的区别”，我觉得可以按这个顺序答：

1. 先说根本区别是“时序由谁生成”
2. 再说硬件 IIC 由外设状态机完成，CPU 占用低
3. 再说软件 IIC 由 GPIO 模拟，灵活但阻塞
4. 再比较速率、时序稳定性、引脚灵活性、移植性
5. 最后落到“项目里怎么选”

这样回答更像是在做技术判断，而不是背概念表格。

## 八、我的选择结论

如果是正式项目，我的默认倾向还是：

**能稳定用硬件 IIC，就优先用硬件 IIC。**

原因很简单：

- 更省 CPU
- 更容易跑高一点的速率
- 更适合长期维护

但如果遇到下面这些条件：

- 专用引脚不方便
- 设备少、速率低
- 调试周期短
- 更强调“先跑通”

那软件 IIC 绝对不是“退而求其次”的方案，反而可能是最现实的工程选择。

## 总结

软件 IIC 和硬件 IIC 的区别，可以最后收成一句话：

- **硬件 IIC 用专用外设换来了更低 CPU 占用和更稳定时序**
- **软件 IIC 用 CPU 手搓时序换来了更强灵活性和更好调试性**

真正的选型，不是死记“谁高级”，而是看你的项目更缺什么：

- 缺性能和稳定性，就偏向硬件 IIC
- 缺引脚和灵活性，就偏向软件 IIC

这类问题真正考的，也不是你会不会背协议定义，而是你能不能把“协议实现方式”映射回 CPU、GPIO、外设状态机和工程约束。
