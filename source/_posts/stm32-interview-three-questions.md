最近面试时被问到了一串很典型的 STM32 底层问题。表面上看，这些问题分散在芯片结构、存储器、烧录和 Flash 读写几个方向，但本质上都在考一件事：你有没有把 STM32 当成一个完整的硬件系统理解，而不只是会调几个库函数。

这篇文章就把这条思路重新捋一遍，从“芯片里有什么”一路走到“程序为什么能从 Flash 里跑”“Flash 为什么好读不好写”。如果把这条线讲顺了，很多面试追问其实就不会乱。

## 面试里这一串问题，本质上在考什么

我这次被追问的内容，大致可以归成下面几类：

1. STM32 最基础的构成是什么，底层到底有哪些东西？
2. STM32 的存储器映射大致怎么分布？
3. SRAM 和 Flash 的用途分别是什么？
4. 为什么程序能直接从 Flash 里运行？
5. Flash 在底层是怎么读写的，为什么擦除按页或扇区？
6. 写 Flash 时怎么避免覆盖原来的数据？

如果把这些问题一个个孤立回答，很容易变成零散知识点。但把它们连起来看，其实就是在沿着这条主线往下走：

**芯片结构 -> 地址空间 -> 存储器分工 -> 程序执行方式 -> Flash 物理限制 -> 读写策略**

## 一、先从最根本的问题开始：STM32 底层到底由什么组成

很多时候我们写代码，只能看到 `main()`、外设初始化函数和中断回调。但这些代码真正能跑起来，依赖的是 STM32 内部一整套硬件结构。

从最基础的角度看，STM32 可以拆成下面几个部分：

- 内核：也就是 Cortex-M 处理器，负责执行指令。
- 存储器：包括 Flash 和 SRAM。
- 总线：负责连接内核、存储器和外设。
- 外设：GPIO、USART、TIM、ADC、SPI、I2C 这些模块都挂在总线上。
- 中断与系统控制：比如 NVIC、SysTick、SCB 这些内核相关模块。

如果再说得直白一点：

- 内核负责“算”
- 存储器负责“放”
- 总线负责“搬”
- 外设负责“和外界交互”

这也是为什么底层开发常常会被概括成一句话：**通过读写寄存器控制硬件行为。**

因为不管是点亮一个 LED，还是发一个串口字节，本质上都是 CPU 通过总线访问某个模块对应的寄存器。

## 二、STM32 的存储器映射到底怎么理解

很多人第一次接触“存储器映射”会觉得抽象，其实可以先把它理解成一句很朴素的话：

**在 STM32 里，代码区、RAM 区、外设区，最终都要被放进统一的地址空间里。**

STM32 基于 ARM Cortex-M 内核，通常面对的是 32 位地址空间，也就是理论上的 `4GB` 寻址范围。这个空间不是全都真的接了物理器件，而是被架构提前划成了几大块，不同区块映射给不同类型的资源。

一个常见的理解框架可以这样记：

- `0x0000_0000` 附近：代码区
- `0x2000_0000` 附近：SRAM 区
- `0x4000_0000` 附近：片上外设区
- `0x6000_0000` 以后：外部存储器或扩展设备区
- `0xE000_0000` 以后：Cortex-M 内核私有外设区

放到 STM32 里，常见含义是：

- 内部 Flash 通常从 `0x0800_0000` 开始
- 内部 SRAM 通常从 `0x2000_0000` 开始
- GPIO、USART、SPI、I2C、TIM 这些外设寄存器映射在 `0x4000_0000` 这一片
- NVIC、SysTick 这类内核级模块映射在 `0xE000_0000` 一带

这件事一旦想通，很多底层代码就不神秘了。比如：

```c
#define GPIOA_ODR   (*(volatile unsigned int *)0x4001080C)

GPIOA_ODR |= (1U << 5);
```

这段代码的本质，不是“调用了某个神秘的硬件接口”，而是 CPU 去访问了一个固定地址，对那个地址上的寄存器位做了修改。

所以所谓“存储器映射”，其实就是：**把外设寄存器也映射进统一地址空间，让 CPU 能用访问内存地址的方式访问硬件。**

## 三、SRAM 和 Flash 的分工，为什么一个适合跑程序，一个适合放程序

理解了地址空间之后，下一个高频追问通常就是：`SRAM` 和 `Flash` 到底各干什么。

### 1. Flash 是掉电不丢的“长期存储”

Flash 的核心特点是：**非易失性**。断电之后，里面的数据还在。

所以它通常负责存这些东西：

- 用户程序代码
- 常量数据
- 查找表
- 固件版本信息
- 少量掉电后也不能丢失的配置参数

STM32 上最典型的情况，就是你的 `.text` 代码段和很多只读常量都在 Flash 里。

### 2. SRAM 是程序运行时的“工作区”

SRAM 的核心特点是：**读写快，但掉电丢失**。

所以它适合放程序运行时的动态数据，比如：

- 全局变量
- 静态变量
- 局部变量
- 函数调用栈
- 动态分配出来的堆空间

可以把它理解成 MCU 的“办公桌”。程序真正运行时，需要不断改来改去的数据，必须放在 SRAM 里。

### 3. 为什么它们要这样分工

因为二者的定位从一开始就不同：

- Flash 适合“保存”
- SRAM 适合“工作”

如果把程序代码全放 SRAM，掉电就没了，而且上电后还得先把代码装进去；如果把所有运行时变量都放 Flash，又会遇到 Flash 写入慢、擦除粒度大、寿命有限这些问题。

所以最自然的分工就是：

- **Flash 存程序和常量**
- **SRAM 存运行过程中的变量和临时数据**

## 四、为什么程序可以直接从 Flash 里运行

这也是面试里很爱追问的点。很多人知道“程序在 Flash 里”，但一被问到“为什么能直接运行”，就容易只剩一句“因为硬件支持”。

更完整一点的说法是：STM32 内部程序执行通常是 **XIP（Execute In Place）**，也就是“就地执行”。

### 1. 先理解什么叫 XIP

XIP 的意思是：**代码存在哪，就直接从哪取指执行，不需要先整体搬到 RAM。**

在 STM32 里，内部 Flash 已经被映射进地址空间，CPU 可以直接对这段地址取指。所以程序复位后，内核能直接去代码区拿复位向量、拿指令、开始执行。

### 2. 为什么内部 Flash 能做到这件事

原因主要有三层：

1. 总线架构允许 CPU 直接从代码区取指。
2. 内部程序存储器本质上是 NOR Flash 一类可随机读取的结构。
3. 芯片通常会配合预取、缓存或加速单元，尽量弥补 Flash 速度慢于内核时钟的短板。

所以从 CPU 的视角看，读取 Flash 指令和读取某块映射地址的数据，本质上都是“按地址访问”。

### 3. 这也是为什么 Flash“好读”

在 STM32 里读 Flash，最直观的方式就是按地址读：

```c
uint32_t value = *(__IO uint32_t *)0x08008000;
```

这行代码没有先发什么“读命令”，也不需要像串口那样走协议。因为对 CPU 来说，这就是一段已经映射好的地址空间。

这也是 Flash 和很多外部块设备最本质的差别之一。外部 NAND、U 盘、硬盘通常不能这样被 CPU 直接按地址取指，而内部程序 Flash 可以。

## 五、Flash 为什么“好读不好写”

理解到这里，Flash 的读其实已经不难了。真正麻烦的是写。

### 1. Flash 的难点不在读，而在写入约束

Flash 不是 SRAM，不能像变量一样随手改某个字节。它有几个很典型的硬件限制：

- 写之前通常要先擦除
- 擦除不是按一个字节擦，而是按页或扇区擦
- 编程时常有半字、字或双字的对齐要求
- 为了防止误操作，控制器通常默认上锁

所以底层写 Flash 的典型流程一般是：

1. 解锁 Flash 控制器
2. 擦除目标页或扇区
3. 按规则写入数据
4. 轮询忙状态或检查错误标志
5. 重新上锁

### 2. 为什么擦除一定按页或扇区

这不是软件故意设计得麻烦，而是 Flash 存储单元的物理结构决定的。

Flash 写入时，本质上通常只能把位从 `1` 变成 `0`。如果想把 `0` 恢复成 `1`，就得执行擦除操作。问题在于擦除需要高压，而且这个高压电路不可能给每一个字节都单独配一套，否则芯片面积和成本都会非常夸张。

所以工程上的折中做法就是：**多个存储单元共用一套擦除资源，形成页或扇区这样的擦除粒度。**

这就解释了为什么：

- 读可以很细粒度
- 写可以按字、半字或字节组织
- 但擦除往往必须按页或扇区来

### 3. 一个最基础的 Flash 读写例子

如果面试官问“那你用标准库写一个最简单的 Flash 读写”，可以这样回答：

```c
uint32_t addr = 0x0800F800;
uint32_t data = 0x12345678;
uint32_t read_back = 0;

FLASH_Unlock();
FLASH_ErasePage(addr);
FLASH_ProgramWord(addr, data);
FLASH_Lock();

read_back = *(__IO uint32_t *)addr;
```

这个例子里：

- `FLASH_Unlock()`：先解锁
- `FLASH_ErasePage(addr)`：擦除目标页
- `FLASH_ProgramWord(addr, data)`：按字写入
- `FLASH_Lock()`：重新上锁
- `*(__IO uint32_t *)addr`：再按地址把数据读回来校验

如果想把回答再往“底层理解”上提一层，可以补一句：

**Flash 的读取像普通内存访问，真正麻烦的是写之前要先擦除，而且擦除粒度通常比写入粒度大得多。**

## 六、写 Flash 时怎么避免把原来的数据一起弄丢

这个问题继续往下追，其实就是在问你：你知不知道 Flash 的“最小擦除单位”和“想修改的数据范围”通常不是一回事。

举个常见场景：

- 你只想改 4 个字节
- 但这 4 个字节所在的整页是 `1KB`
- 擦除时会把这 `1KB` 全部清掉

如果直接擦，那这一页里别的有效数据也会一起丢。

### 正确思路：读-改-写

工程上最经典的做法是 **Read-Modify-Write**：

1. 先把目标页整个读到 SRAM 缓冲区
2. 在 SRAM 里只修改你关心的那几个字节
3. 擦除原来的 Flash 页
4. 再把 SRAM 里的整页数据完整写回去

这个思路的关键不是库函数，而是你是否意识到：

- 擦除是大粒度的
- 修改往往是小粒度的
- 所以中间必须借助 SRAM 做过渡缓冲

如果再往工程一点的方向延伸，还可以继续补：

- 高频写入要考虑 Flash 擦写寿命
- 配置参数区要尽量和代码区分开
- 更复杂的场景会做日志式存储、版本头、CRC 校验和磨损均衡

## 七、如果把这条面试回答链路顺下来，可以怎么讲

我后来发现，这类问题其实很适合按一个固定顺序回答：

1. 先讲 STM32 由内核、总线、存储器、外设组成
2. 再讲所有资源都被映射到统一地址空间
3. 再区分 Flash 和 SRAM 的职责
4. 再解释程序为什么能直接从 Flash 取指执行，也就是 XIP
5. 最后再落到 Flash 的物理限制和读写流程

这样回答的好处是，你不会一上来就掉进某个零散 API 里，而是始终站在“硬件结构 -> 软件行为”的视角往下讲。

## 总结

这次面试里的这些追问，让我重新意识到一件事：STM32 底层知识不能只靠零碎记忆。

更好的整理方式应该是：

- 先从芯片结构入手
- 再理解地址空间和存储器映射
- 再区分 Flash 和 SRAM 的职责
- 再理解 XIP 为什么成立
- 最后把 Flash 读写放回物理限制里看

这样你回答的时候，就不会只停留在“库函数怎么调”，而是能真正讲清楚：

- STM32 底层到底由哪些部分组成
- 存储器为什么要统一编址
- 为什么程序能从 Flash 直接运行
- 为什么 Flash 好读不好写
- 为什么改一点数据也可能要整页搬运

对我来说，这不只是几道面试题，更像是一次提醒：  
真正的底层能力，不是会几个函数，而是能把代码背后的硬件逻辑讲顺。
