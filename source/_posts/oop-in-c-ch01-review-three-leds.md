最近在看《C 语言面向对象编程·嵌入式实战》这本书。第一章《三个 LED 三份代码，第一次面对重复》看起来像是在讲一个很简单的 LED 例子，但我发现它真正要解决的，并不是“怎么点亮一个灯”，而是“面对很多颗灯、很多份重复逻辑时，代码应该怎么组织”。

这篇文章我想保留自己一开始的理解，再把后面和 AI 反复讨论之后修正过的部分也一起写下来。这样既是一次学习复盘，也能把自己从“差不多懂了”走到“理解更准确了”的过程留下来。

## 我一开始的理解

我刚看完这一章时，最先写下来的理解大概是这样的：

> 这一节主要讲的是面对三份同样功能的代码，比如点亮 LED 灯；可以使用封装，把相同的部分统一管理起来。这样不仅可以节省代码量，还可以应对修改时的方便。主要的实现方法就是通过一个指针 me，指向这个封装的结构体。实现函数也是同样调用这个指针，像初始化，开关，亮度调节。

后来我又进一步理解成：

> `struct led` 里存放的就是每个 LED 的区别，也就是引脚、亮度，还有开关状态。实现函数也就是相同的部分，比如初始化、亮灭，还有亮度调节。

再往后我还补了一句：

> 如果 `pin` 写死在 `led_on` 里，那软硬件都互相锁死了。

这些理解其实已经抓到了这一章的一部分重点，但还不够准确，里面也混进了一些后面章节的概念，或者把一些次要现象误当成了核心原因。

## 哪些地方我理解对了

先说对的部分。

### 1. 这一章确实是在解决“重复代码”问题

书里最开始给出的代码，就是红灯、绿灯、蓝灯各写一份 `on/off` 函数：

```c
void red_led_on(void)  { ... }
void red_led_off(void) { ... }

void green_led_on(void)  { ... }
void green_led_off(void) { ... }

void blue_led_on(void)  { ... }
void blue_led_off(void) { ... }
```

表面看每个函数都很短，也能跑，但一旦硬件改版、引脚调整、功能扩展，问题就会马上暴露出来。

### 2. 这一章确实用了“封装”的思想

它做的事情，就是把一颗 LED 相关的数据收进 `struct led`，再让一套统一函数去操作这个结构体实例。

也就是：

- 数据收进对象
- 共同行为写成统一函数
- 调用时通过 `me` 知道当前操作的是谁

### 3. `struct led` 的确在保存每个对象自己的信息

这一章里的 `struct led` 主要长这样：

```c
struct led {
	uint8_t pin;
	uint8_t brightness;
	bool    is_on;
};
```

这里面装的是某一个 LED 实例自己的信息，而不是所有 LED 共用的一份全局状态。

## 哪些地方我一开始理解得还不够准确

真正有价值的复盘，不是只说自己哪里理解对了，更重要的是知道哪里“看起来懂了，其实还差半步”。

### 1. 这一章的重点不只是“节省代码量”

我一开始说“这样可以节省代码量”，这不算错，但不够到位。

这一章真正重要的不是少写了几行代码，而是：

- 以后加 LED，不需要复制出一堆同构函数
- 以后改引脚，不需要到处搜、到处改
- 以后加 `toggle`、`deinit`、`set_brightness` 时，不会把重复逻辑越堆越多

也就是说，它更核心的价值是：**减少改动扩散，降低维护成本。**

### 2. `me` 指针的作用，不是“避免程序变大”这么简单

我一开始会把 `me` 理解成“值传递会让程序越来越大，所以用指针更好”，这个理解太表层了。

更准确地说，`me` 的作用是：

- 告诉函数“现在操作的是哪一个 LED 对象”
- 让函数能直接访问并修改这个对象内部的状态
- 让一份统一逻辑能服务不同实例

比如：

```c
int led_on(struct led *me)
{
	if (!me)
		return -1;

	me->is_on = true;
	platform_gpio_write(me->pin, true);
	return 0;
}
```

这里的 `me` 本质上就是“把这张挂号单递给函数”。  
函数并不是抽象地“点灯”，而是在点“这颗由 `me` 指向的 LED”。

### 3. `pin`、`brightness`、`is_on` 不应该都简单叫“区别”

我一开始说 `struct led` 里放的是“每个 LED 的区别”，这句话方向有点像，但还不够细。

更准确的划分应该是：

#### 配置或身份信息

- `pin`

它表示这个 LED 绑定的是哪个硬件引脚，这更像“这个对象是谁”。

#### 运行时状态

- `brightness`
- `is_on`

它们表示这个对象当前处于什么状态，这更像“它现在怎么样了”。

所以 `struct led` 里装的，不只是“天然不同”的东西，也包括“运行过程中会变化”的状态。

### 4. 我把 `ops` 提前想进来了，但这一章其实还没到那一步

我当时说自己“对 `ops` 表还不太了解”，后来回头看才发现，这个困惑其实并不属于第一章。

第一章只是在建立最朴素的对象模型：

- 一个 `struct` 代表一个对象
- 一个 `me` 指针把对象递给函数
- 一份函数复用到多个对象上

`ops` 表是后面“多态层”的内容，它解决的是“同一个接口，为什么可以有不同实现”。  
第一章还只是封装层，不需要提前把多态混进来。

## 这一章真正想让我建立的模型

如果把这一章压缩成一句最核心的话，我现在更愿意这样说：

**把“变化的数据”和“不变的逻辑”分开。**

具体到这个 LED 例子里：

- 不变的是 `led_on / led_off / led_toggle / led_set_brightness` 这些行为逻辑
- 变化的是每个 LED 自己的 `pin`、`brightness`、`is_on`

所以正确的组织方式就变成：

- 每颗 LED 开一张属于自己的“挂号单”，也就是 `struct led`
- 共同行为只写一份
- 调用时把“当前这张单子”通过 `me` 传给函数

这就是书里所谓的“封装”。

## 为什么 `pin` 不能写死在 `led_on()` 里

这一点是我后来才真正想清楚的。

如果 `pin` 直接写死在 `led_on()` 里，比如它永远只写 `PA.13`，那这份函数就只能服务一个固定 LED。这样会带来几个连锁问题。

### 1. 失去复用性

如果 `led_on()` 只能操作一个固定引脚，那第二颗、第三颗 LED 就只能继续复制出：

- `green_led_on()`
- `blue_led_on()`

重复代码问题又回来了。

### 2. 硬件改版时容易改漏

如果红灯从 `PA.13` 改到 `PA.7`，所有写死这个引脚的地方都要一起改。  
只要漏掉一个函数，就会出现“有的地方还在操作旧引脚，有的地方已经换成新引脚”的错误。

### 3. 软件和硬件绑定得太死

逻辑层本来应该描述“点亮某颗 LED”，而不是“无论如何都去写某一个固定引脚”。  
一旦把 `pin` 写死在函数里，这份函数就不再是“通用逻辑”，而变成了“某个硬件细节的散装封装”。

所以我后面才会把那句“软硬件都互相锁死了”理解得更具体一些：  
不是抽象意义上的“锁死”，而是**代码失去复用能力，硬件变动会引发大面积修改。**

## 为什么 `brightness` 和 `is_on` 不能做成全局变量

这一点我后来也想通了。

如果把 `brightness` 和 `is_on` 做成全局变量，那么它们就不再属于“某一颗 LED”，而变成系统里大家共用的一份状态。这样的问题非常直接：

### 1. 状态会串台

红灯把 `is_on` 设成 `true`，绿灯又把它改成 `false`，你就很难说这个状态到底属于谁。

### 2. 一份变量描述不了多个对象

三颗 LED 明明各有自己的开关状态和亮度状态，但全局变量只有一份。  
一份共享变量，表达不了“每个对象各自的状态”。

### 3. 函数和对象的归属关系会变模糊

如果 `led_set_brightness()` 修改的是某个全局变量，那它操作的就不是“某个 LED 对象的状态”，而是“系统里一份公共状态”。  
这样写，代码的对象感就丢了。

所以更准确的理解是：

- `pin` 是对象的配置或身份信息
- `brightness` 和 `is_on` 是对象的运行时状态

它们都应该收进 `struct led`，由每个对象自己保存、自己维护。

## 这一章在整本书里的位置

这一点是我现在回头看，感觉特别重要的一件事。

第一章不是孤立在讲一个 LED 例子，它其实是在给后面整本书打地基。

它所在的位置，我会把它放在整个知识网格里的**封装层**：

- 作用：建立“对象 = 数据 + 操作该数据的统一函数”这个最小模型
- 解决的问题：重复代码、状态散落、改动扩散
- 为后面支撑的内容：
  - 第二章的信息隐藏
  - 第三章里更像 `class` 的写法
  - 后面的继承
  - 再后面的 `ops`、多态、platform 抽象

换句话说，如果第一章没有把“一个对象有自己的数据”和“一份逻辑可以服务多个对象”这件事想透，后面看 `ops`、`container_of`、Platform 层，就很容易一直别扭。

## 我现在更准确的复盘版本

如果让我用现在的理解，重新复述这一章，我会这样说：

> 这一章主要解决的是 LED 控制代码重复的问题。三个 LED 的控制逻辑本质上是一样的，真正不同的只是每个 LED 自己的引脚和状态。所以书里把这些数据收进 `struct led`，让每一颗 LED 都有一份属于自己的对象数据；再把初始化、开关、翻转、亮度调节这些共同逻辑写成统一函数。函数通过 `me` 指针知道当前操作的是哪一个对象，从而实现“一份代码服务多个 LED”。这就是最朴素的封装。它的价值不只是减少代码量，更重要的是把差异和共性分离，减少改动扩散，让代码在硬件改版和功能扩展时更容易维护。 

## 这章留给我的两个检查题

为了避免自己只是“看懂了这篇复盘”，我想把这两个问题留给自己继续反复问：

1. 如果 `pin` 写死在 `led_on()` 里，这份函数为什么就不再是通用逻辑？
2. 如果 `brightness` 和 `is_on` 做成全局变量，为什么会破坏“每个 LED 管自己的状态”？

我感觉第一章真正的难点，不在语法，而在于要把脑子从“我在写几个函数”切换到“我在组织一组对象和它们的行为”。

这一步一旦跨过去，后面再看 `me`、`this`、`ops`、多态这些概念，才会真正顺起来。
